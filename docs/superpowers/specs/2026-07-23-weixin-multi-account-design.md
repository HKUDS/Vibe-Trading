# Weixin Multi-Account Channel Design

## Context

Vibe-Trading currently exposes one built-in `weixin` channel backed by one
`WeixinChannel` instance and one persisted iLink account state file. The
installed primary account is active, has a valid QR-derived token, and is in
daily use. The operator wants two to three Weixin ClawBot accounts to connect
to the same Vibe-Trading backend without replacing the current account or
mixing conversations between accounts.

The Weixin ClawBot entry is a Weixin functional contact rather than a normal
shareable contact. Additional users therefore need their own QR-authorized
ClawBot account instead of being invited to the existing private chat.

## Goals

- Keep the current account online as the backward-compatible primary account.
- Support two to three concurrently polling Weixin accounts in one channel and
  one Vibe-Trading backend.
- Preserve the primary account token, pairing approvals, and session mapping
  without requiring another QR login.
- Isolate account credentials, polling cursors, context tokens, pairing
  identities, and agent sessions.
- Make one account failure non-fatal to the other accounts.
- Add account-aware login and sanitized account status without exposing Weixin
  identifiers or credentials.
- Provide a tested, reversible rollout with Git, Docker-image, and runtime-state
  recovery points.

## Non-Goals

- Sharing one ClawBot functional contact with other Weixin users.
- Running one Docker container per Weixin account.
- Adding group-chat authorization as part of this change.
- Per-account model providers, workspaces, tool permissions, or billing.
- Live broker execution or changes to the existing trading safety boundary.
- Dynamic account hot-reload. Enabling a newly logged-in account may require a
  short container recreation.

## Compatibility Invariants

The existing top-level `channels.weixin` section remains the primary account.
When no auxiliary `accounts` mapping is present, behavior must remain equivalent
to the current single-account implementation.

The primary account keeps all existing identifiers and paths:

- Account alias: `primary`
- State file: `~/.vibe-trading/runtime/weixin/account.json`
- Pairing identity: the existing raw sender ID under pairing channel `weixin`
- Session key: the existing `weixin:<chat_id>` format

The implementation must not rename, move, rewrite, or delete the primary state
file during upgrade. Existing pairing approvals and session-map entries remain
valid without migration.

## Configuration

The primary account continues to use the existing top-level fields. Auxiliary
accounts are added under an optional `accounts` mapping:

```json
{
  "channels": {
    "weixin": {
      "enabled": true,
      "allow_from": [],
      "accounts": {
        "account2": {
          "enabled": true,
          "allow_from": []
        }
      }
    }
  }
}
```

Auxiliary account aliases must match `[a-z][a-z0-9_-]{0,31}`. The reserved
alias `primary` is rejected inside `accounts`. Each auxiliary account supports
only account-scoped operational fields needed by the existing adapter:

- `enabled`
- `allow_from`
- `base_url`
- `cdn_base_url`
- `route_tag`
- `poll_timeout`

QR-derived tokens are never stored in `agent.json`. Auxiliary state directories
are computed from the validated alias and cannot be overridden through config.

## Architecture

`WeixinChannel` remains the only channel registered with `ChannelManager`. It
becomes an account router that owns one `WeixinAccountRuntime` per configured
account. The account runtime contains the state currently held directly by
`WeixinChannel`:

- HTTP client
- bot token
- get-updates cursor
- context-token cache
- typing-ticket cache
- processed-message cache
- long-poll task and retry state
- account-specific state directory

The primary runtime uses the legacy state directory. Auxiliary runtimes use:

```text
~/.vibe-trading/runtime/weixin/accounts/<account-alias>/account.json
```

The channel starts one asynchronous polling task per enabled account. Account
startup, retry, shutdown, and state persistence are isolated. A failure in an
auxiliary task updates that account's status but does not cancel the primary or
other auxiliary tasks.

## Message Routing

Primary inbound messages retain their raw sender and chat IDs, preserving the
existing authorization and session behavior.

Auxiliary inbound messages use one opaque internal route key generated by a
single helper:

```text
weixin-route:v1:<account-alias>:<base64url-peer-id>
```

The route key is used as the auxiliary `sender_id` and `chat_id`. This gives the
existing runtime a unique session key without changing shared channel-runtime
interfaces. It also prevents identical peer IDs on different accounts from
colliding.

For outbound traffic, `WeixinChannel.send()` distinguishes a primary raw chat
ID from an auxiliary route key. It validates and decodes the route key, selects
the account runtime, restores the remote peer ID, and sends through that
account's token and context-token cache. Invalid or unknown routes fail closed
and never fall back to the primary account.

Route encoding is an internal routing mechanism, not an authentication or
secrecy mechanism. Raw and encoded peer identifiers must not be returned by the
public status endpoint.

## Authorization And Pairing

Primary authorization remains byte-for-byte compatible with the existing
top-level `allow_from` list and pairing records.

Each auxiliary runtime evaluates its own raw `allow_from` list. If a sender is
not explicitly allowed, pairing uses the auxiliary route key as the stored
sender identity under channel `weixin`. This keeps the existing pairing-store
schema compatible while making approvals account-specific.

Wildcard authorization is never generated automatically. The installed
operator configuration continues to use empty allowlists and explicit pairing.
Force-login, revoke, or pairing operations for one auxiliary account must not
modify another account's token or approvals.

All approved accounts share the same Vibe-Trading backend, configured model API,
workspace, research files, and tool permissions. Account isolation prevents
conversation mixing; it does not create separate data-security tenants.

## Sessions

The primary account continues to resolve sessions through the existing
`weixin:<chat_id>` session-map key.

Auxiliary accounts naturally resolve through
`weixin:<weixin-route-key>`. No existing primary session-map entry is rewritten.
The `/new` and reset commands operate on the routed session key, so a reset on
one account cannot reset another account's conversation.

## Login And Account Lifecycle

The channels login command gains an optional account selector:

```text
vibe-trading channels login weixin --account account2
```

Omitting `--account` preserves the existing primary login behavior. An
auxiliary alias must already exist in config before login. `--force` removes
only the selected account's state file and never touches other accounts.

Recommended auxiliary-account onboarding is:

1. Add the auxiliary config with `enabled: false`.
2. Run account-scoped QR login while the primary service remains online.
3. Verify the selected auxiliary state file contains a non-empty token without
   printing the token.
4. Set the auxiliary account to `enabled: true`.
5. Recreate the service and verify both accounts.
6. Complete pairing and an exact-response test on the auxiliary account.

Background startup never launches an invisible QR flow. An enabled account
without a valid token reports `login_required` and remains stopped.

## Status And Observability

The existing top-level Weixin status remains available. `running` is true when
at least one enabled account is running. A nested account map reports only:

- alias
- configured
- enabled
- loaded
- running
- login required
- sanitized error category

Status and logs must not include tokens, context tokens, QR identifiers, bot
IDs, Weixin user IDs, peer IDs, or raw route keys. Operational logs may name the
operator-defined account alias.

## Failure Handling

- Invalid, duplicate, reserved, or path-unsafe aliases reject configuration.
- Missing auxiliary credentials produce `login_required`; they do not trigger
  QR login during background startup.
- Authentication failure preserves the state file for diagnosis and rollback.
- Network and long-poll failures retry per account using existing backoff rules.
- One account task failure cannot cancel sibling account tasks.
- State writes remain atomic and occur only inside the selected account runtime.
- Shutdown stops and persists every runtime independently.
- An invalid outbound route fails closed and is not sent through another account.

## Engineering Isolation And Backup

Implementation occurs in a dedicated Git worktree and feature branch. Changes
are committed in reviewable increments. Local Compose overrides, `agent.env`,
`agent.json`, tokens, pairing records, session mappings, and backup archives are
never committed.

Before production cutover:

1. Record the pre-change Git commit.
2. Tag the currently running Docker image for rollback.
3. Create an ACL-restricted local snapshot of Weixin account state, pairing
   state, and channel session mappings outside the repository.
4. Grant snapshot access only to the current Windows user and `SYSTEM`.
5. Validate that the snapshot exists without printing secret contents.

The implementation is non-destructive to legacy state, so rollback normally
requires only recreating the service from the old image. The protected snapshot
is used only if runtime state was unexpectedly changed or corrupted.

## Testing

Focused tests cover:

- legacy configuration with no `accounts`
- primary state-path and session-key compatibility
- auxiliary alias validation and state-path confinement
- account-specific state load/save and force login
- route-key encode/decode and malformed-route rejection
- correct outbound account selection
- simultaneous inbound messages from two accounts
- identical peer IDs on different accounts
- per-account allowlists and pairing identities
- per-account `/new` session reset
- one-account startup, poll, send, and shutdown failure isolation
- sanitized account status and logs
- CLI default-primary and `--account` behavior
- no token overwrite between accounts

Regression verification includes the existing packaging, channel runtime, CLI
channels, Weixin adapter, LLM, and provider-default tests plus Ruff checks for
all touched Python files.

## Rollout

Rollout is deliberately split into two short service recreations:

1. Build and test the candidate image while the current container stays online.
2. Create the Git, image, and protected runtime recovery points.
3. Recreate the service with multi-account code but no auxiliary account enabled.
4. Verify HTTP health, primary token presence, primary account running status,
   existing pairing count, and absence of a new QR prompt.
5. Ask the operator to send one exact primary-account reply test.
6. If primary verification fails, restore the old image immediately and stop.
7. Configure and QR-login `account2` while the primary account remains online.
8. Recreate the service with `account2` enabled.
9. Verify both account runtimes, independent pairing, exact replies, and session
   isolation.

Each recreation is expected to interrupt Weixin processing for approximately
15 to 60 seconds on the current host. Windows is not restarted. The operator is
not asked to re-scan the primary account during a normal upgrade.

## Acceptance Criteria

- The current primary account resumes after upgrade without QR login.
- Existing primary pairing and session mappings remain valid.
- Two accounts can poll and reply concurrently through one Vibe-Trading backend.
- The same peer ID on two accounts produces separate agent sessions.
- Failure or forced login of one auxiliary account does not affect the primary.
- No credential or Weixin identifier appears in Git, public status, or reported
  verification output.
- Rollback to the pre-change image restores the previous single-account service
  without QR login.
